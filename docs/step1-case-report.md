# Step1 케이스 리포트 — 스크린샷 → 포트폴리오 데이터화 (2026-08-10)

Step1의 목표: 계좌별 (종목, 수량, 매수가)의 정확한 데이터화. 얻을 수 없는 값은 비운다 —
채점은 "정말 얻을 수 없는 값인가"의 정확성(근거 없이 채움 = 오류, 화면에 있는데 비움 = 오류).
흐름은 단방향 1회: 추출 → 표시 → 사용자 확인/수정 → Step2.

## 2. 백엔드 두 경로 (+비결정성 실측)

한 서버·한 엔드포인트, 요청의 `engine` 필드로 선택:

- **edge** — OCR(RapidOCR PP-OCRv5)+기하 바인딩. LLM 0개, 폰(APK)과 같은 경로. 1.4~2s/장.
  **완전 결정적**(전 케이스 반복 실행 바이트 동일).
- **orin** — VLM `qwen2.5vl:3b-ft3-q8`(로컬 ollama) + 증권사 검색·판독. 8~14s/장.
  값 축 결정적(신선 3라운드에서 키·값 칸 차이 0). 유일한 요동은 게이트가 어차피 기각하는
  현재가 오독의 문구(NVDA 226.76↔227.42) — 최종 데이터에 무영향.

과거 배치들의 종목 수 요동(같은 세트 28→38 등)은 코드 진화 산물이었다 — 현행 코드 재실행에서
두 엔진·순서 셔플 모두 동일 종목 수로 수렴.

## 3. 발견한 근본 문제 4 + 수정

전부 원본 이미지·raw로 검증 후 수정. VLM 재학습이 필요한 결함은 없었다 — 값 축 결함은 전부
**공용층(bind/finalize)**.

### P1. 같은 계좌의 화면 간 병합 부재 (최중대, 공용층)
- 증상: 같은 계좌를 재캡처·스크롤 겹침으로 여러 장 올리면 같은 자산이 화면 수만큼 복제.
  '한 자산 한 행' 불변식이 화면 안(`seen_vals`)에만 있었다.
- 실측: G5/G8/G9에서 삼성 IRP 7행·ISA 4행이 2중 계상. G9 라이브 결과(8/7~8/9)의
  '42종목·277.7M'은 **유령 자산 33.5M(12%)이 낀 값** — 실제는 31종목·244.2M.
  G6(픽스처)는 화면 간 자산 겹침이 없어 한 번도 드러나지 않았다.
- 수정: `finalize._merge_across_screens` — 강한 키(계좌번호 토큰 교집합+이름)는 값이 달라도
  1행 채택+경고, 약한 키(증권사+유형+이름, VLM 경로)는 값 동일할 때만 병합·다르면 둘 다
  유지+'중복 의심' 경고(틀린 병합은 이중 계상보다 나쁘다). 병합은 무손실 — 빈 수량·매수가를
  상대 화면에서 보완.

### P2. 예수금 탭의 3중 계상 / 외화예수금 누락 (bind)
- 증상: SMART 원화예수금 탭에서 예수금(당일) 48.8M + 추정예수금 44.2M + 현금 40.2M이 각각
  자산 행으로(같은 돈 3번). 외화예수금 탭은 반대로 미국달러 행이 통째 누락(false abstain).
- 원인: 접기 근거인 화면 헤더 카드('원화 예수금 (D+2) 44,186,151')를 바인더가 못 잡았고,
  '환율 1,482.00' 같은 자기값 라벨이 최근접 분할에서 환산액을 훔쳐갔다(같은 폼이 G1에서는
  그 라벨이 2회 반복돼 크롬 필터에 걸린 덕에 — 운으로 — 살았다).
- 수정: ① 자기값 라벨·어포던스(`접기›`)를 짝짓기 전에 배제 ② 외화 행의 환산액 폴백 부착
  ③ 상단 총액 카드 캡처(`bind._card_total`) ④ `_drop_deposit_echoes`의 접기 근거에 화면
  자신의 카드 총액 추가. 결과: 예수금 1행(D+2 헤더값), 미국달러 6,928.52 USD 복원.

### P3. mPOP 종합잔고 헤더 총액 미바인딩 → 오경보 (bind)
- 증상: 상세행 합이 헤더 '자산'과 **원 단위까지 일치**하는 화면(실측 2건: 35,517,145 /
  935,184)이 자기검증을 못 해, 다른 화면의 예수금과 비교되는 "환각 의심" 오경보.
- 원인: 헤더드 경로가 컬럼헤더 위 영역을 통째로 버려 '자산 35,517,145원' 카드가 유실.
- 수정: `_card_total`이 헤더 위 카드를 `__screen_total__`로 캡처. 효과: **G4(요약·GT 없는
  최난 세트)의 8/8 화면이 화면 총액 원 단위 자기검증 통과.**

### P4. 경고 의미 계층 — '검증 실패'와 '검증 불가'가 한 문구 (finalize)
- 증상: 요약 없는 세트에서 전 화면에 "환각·오추출 의심" 남발 → 진짜 경고가 묻힘.
- 수정: 대조할 총액이 없으면 "검증 불가 — 요약·총액 화면을 함께 올리면 검증된다"로,
  화면 총액 불일치는 "스크롤에 가려 안 찍힌 행이 있으면 이어서 내린 화면을 추가 업로드"로
  행동 가능하게 분리. G3의 -1,825,600 경고는 **진짜 검출**(스크롤 아래 행 잘림)로 확인 —
  게이트 로직 자체는 옳았다.

부수 수정: 현금행 currency 기본 KRW(edge↔orin 표기 통일), accountType '퇴직연금'→'IRP'
통일(같은 계좌가 경로마다 두 이름), parity 판정식에 **cost(매수가) hard 승격**.

## 4. 신규 증거 축 — 업로드 파일명

안드로이드 스크린샷 파일명에는 캡처 앱과 시각이 박힌다(`Screenshot_20260709_160338_ mPOP.jpg`).
프론트가 `names[]`를 동봉하고, finalize가 **화면 근거가 전무할 때만** 마지막 근거로 쓴다
(약한 증거 — 출처 `broker_src: filename`으로 표시, 사용자 확인 UI 대상).

- 실측(G7 = 화면에 증권사 근거가 전혀 없는 mPOP 상세 단독):
  edge → broker 'mPOP'(filename, 확인 UI로 정규명 입력) / orin → 검색+LLM이 **삼성증권 자동
  확정**(research). 수정 전에는 양쪽 다 '미상'.
- EXIF 없는 업로드의 캡처시각도 파일명에서 폴백(`captureSource: filename`).
- 화면 근거가 있으면 파일명은 쓰이지 않는다(우선순위: 정규명 > 상속 > 화면 브랜드 > 파일명).

## 5. 제3의 방법 검토 — T1.5 "값=기하, 라벨=소형 LLM" → **기각**

제안: 값 축은 OCR+기하 유지, 라벨 축(브랜드→정규명)만 온디바이스 소형 텍스트 LLM.
실측으로 기각:

- abstain 프롬프트("불확실하면 UNKNOWN"): 3B-FT·7B·32B 전부, 유명 브랜드(영웅문·나무)까지
  **전부 UNKNOWN** — 커버리지 0.
- 완화 프롬프트: 32B가 가짜 브랜드(ZetaTrade) 포함 **전부 'NH투자증권' 날조** —
  검색 마이닝 날조(DECISION 실측)와 같은 패턴.
- 결론: 로컬 모델의 파라메트릭 지식으로 브랜드→정규명은 어느 스케일에서도 불가.
  값 축은 이미 기하가 완벽(아래 §6)해 LLM이 개선할 것이 없다.

실질적 제3의 방법은 **"OCR+기하 + 파일명 증거 + 사용자 1회 확인(라벨만)"**으로 수렴 — 구현 완료.

## 7. 표시·확신도·사용자 수정 루프 점검 (Step1 완결 조건)

  전부 편집 가능, 편집 시 `*_src: manual`로 승격(확인으로 간주). 행 삭제 가능.
  브랜드/파일명 broker는 정규명 확인 입력(이 배치에만 적용, 저장 안 함 — 캐시 금지 규칙).
- 수정값이 그대로 Step2 입력이 된다(재게이트 없음, avgCost는 cost/qty로 동결 저장).

## 8. 모바일·프라이버시 최종 판정

**결론: 개인정보를 기기 밖으로 내보내지 않고 모바일에서 도는 방법은 성립한다.**

- **값 축(계좌·종목·수량·매수가)**: edge(OCR+기하)가 전 케이스에서 orin과 값 칸 단위 일치,
  G6 GT 기준 cost 포함 전 필드 정답. 신경망 LLM 0개·GPU 불필요·완전 결정적.
- **밖으로 나가는 것**: `outbound.py` 단일 통로 3종이 전부 — symbol(종목명 1개, naver),
  quote(심볼 1개, yahoo), broker(브랜드 토큰 1개, naver·orin 전용). **스크린샷·계좌번호·
  수량·금액은 어떤 경로로도 나가지 않는다.** APK는 `PF_OUTBOUND=prices`로 broker 검색까지
  차단 + `BIND=127.0.0.1`. 시세까지 끊으면(`none`) 완전 오프라인 — 현재가 갱신만 포기.
- **온디바이스의 실한계 1개**: 증권사 **정규명**. 화면·파일명에 브랜드('Super365'·'mPOP')까지만
  있으면 정규명 매핑에 외부 지식이 필요하다 — 로컬 LLM 지식은 불가(§5), 검색은 프라이버시상
  차단. **해소 경로 = 계좌요약 화면 1장 동봉(자동 상속) 또는 사용자 1회 확인(UI 구현됨).**
  값·수량·매수가에는 영향 없음(그룹핑 라벨일 뿐).
- **서버(orin)가 더 잘하는 것**: 브랜드→정규명 자동 확정(검색+LLM) 하나뿐. 그때도 나가는 것은
  브랜드 토큰 1개다.

## 8+. 추가 케이스 — 신규 증권사 폼 3종 (2026-08-10 폰 업로드, 9장)

**증상**: edge가 새 앱 화면의 종목을 전수 누락 — 카카오페이증권 5행→1행, 토스증권 1행→0행,
mPOP ISA 단가 모드(보유수량|매수단가/현재가, 평가금액 열 없음) 값 전무. orin은 단가 모드에서
매수단가를 value로, 현재가를 cost로 오배정(합 181,985 vs 화면 총액 1,020,352 — 82% 오차).

**근본 원인 — 앱별 지식 부족이 아니라 파이프라인의 잘못된 가정**:
① 수량은 정수라는 가정(소수점 매매 '0.056979주' 붕괴) ② 금액·수익률 결합 표기는 금액-우선이라는
가정('+33.28%(74,920원)' 손익 유실) ③ 헤더 어휘 **부분일치**의 저정밀 — 정렬 토글 줄
('평가금액 순'·'평가금'·'현재가' 버튼)이 가짜 헤더가 되어 미지 폼이 일반 경로(리스트 모드)에
도달하지 못함 ④ 로고 조각('S&P' 배지)의 값 탈취.

**일반화 수정(앱별 분기 0)**: `QTY_RE` 소수 허용 / `_amount_of` 수익률-우선 지원(부호는 앞
조각) / `find_header` 완전일치화(미지 폼 → 리스트 모드 관문) / 줄당 최광폭 라벨 1개 /
수량·외화는 좌측정렬 우선 짝짓기 / `H_COST_UNIT` 분리 + 화면 산식(cost=수량×매수단가,
value=수량×현재가 — 값-모드 캡처와 원단위 일치) / **부호 규칙**(부호 금액은 값이 아니라
손익 — '총 수익'류 카드 지표가 어휘 없이 소멸) / **카드 총액 sum-match 폴백**(Σ행≈상단
금액이면 어휘 없이 총액 — 자기검증) / **총액 심판**(화면 총액이 기하를 인증하고 VLM을
반증하면 그 화면의 값 축은 기하 — USD 네이티브 화면 제외로 이중환산 차단) /
`_fill_from_geom` 이름 조인 확장(단가 모드처럼 VLM에 값이 없어도 되메꿈).

**최종**: edge·orin 모두 37행(추정 수량 0), 소수 수량 6행 정확, Voo→VOO 해석, 화면 총액
전 화면 대조 통과. 회귀 게이트 — G9 raw diff 변화 1건('접기' 가짜 행 소실, 의도된 개선),
G6 parity 값 축 30/30 + 음성 대조군 4종 + 셔플 불변 유지. **일반화 계약**: 헤더 어휘가
정확히 맞으면 다열 헤더드 경로, 아니면 무어휘 리스트 모드 + 산술 게이트 + 화면 간 병합 +
사용자 확인 — 새 폼은 커스터마이징 없이 이 경로로 처리된다.
