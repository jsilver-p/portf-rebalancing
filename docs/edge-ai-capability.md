# 엣지 AI 역량 지도 — 민감정보 온디바이스 처리 (진행 중)

목적: 민감정보(증권사 스크린샷)를 다루는 에이전트를 **엣지 안에서만** 구현할 때 어느 수준까지
가능한지, 그리고 그 수준을 얻으려면 무엇이 필요한지를 **실측으로** 파악한다. 목표 기기는
Galaxy S23(8GB, Adreno 740), 합격선은 **제3자 배포**(서명 APK 설치·동작)다.

상태: **Track A Stage A1 통과 ✅** (`parity.py --no-llm --controls`, 비전 LLM과 동일 채점기·동일 기준).
아래 수치는 전부 실측이며, 미달 항목도 그대로 적는다.

---

## 1. 왜 "커스텀 FT VLM을 폰에 올리기"가 막히는가 (스펙 판정)

| 제약 | 실측/출처 | 결과 |
|---|---|---|
| Termux ollama 가속 | 2026-05 기준 **CPU 전용**(Vulkan/NPU 없음) | GPU 경로 없음 |
| llama.cpp OpenCL 검증 GPU | **Adreno 750(8 Gen 3)부터.** S23=Adreno **740**은 목록 밖 | 가속 불확실 |
| 모델 크기 | `3b-ft3-q8` = 4.63GB (LLM 3.29 + mmproj 1.34) | 8GB 기기에 안 들어감 |
| q4 정확도 | DECISION v2.6: 3b-ft q4 **칼날 마진 FAIL** | 축소 후보 없음 |
| prefill 비용 | 3.8B × 2 × 7.5k토큰 ≈ 5.7e13 FLOP, 폰 CPU 30~100 GFLOP/s | **10~30분/장** |
| **Play 배포 한도** | base 모듈 **압축 200MB** / 총 설치 **4GB** | 4.63GB는 **배포 불가** |
| 온디바이스 LoRA | LiteRT-LM은 **Gemma-2 2B·Gemma 2B·Phi-2, 어텐션 레이어, GPU 백엔드**만 | 우리 FT 자리 없음 |

> **핵심 제약: Android에서 가속기 접근과 커스텀 파인튜닝은 상호 배타적이다.**
> 가속기(NPU/GPU)는 플랫폼 API(ML Kit·LiteRT-LM)로만 닿고, 그 API는 플랫폼이 축복한 모델만
> 받는다. 커스텀 FT 가중치를 쓰려면 범용 런타임으로 내려와야 하고 거기엔 가속기가 없다.
> **T1이 이 딜레마를 유일하게 빠져나간다** — 모델이 12.9MB이고 플랫폼 제공(=가속·배포 가능)이며
> **커스텀 지능은 코드에 있다**(코드엔 크기 상한도 화이트리스트도 없다).

> **T2 rung은 1B와 4B 사이에 있다.** 4B는 T1이 비운 칸(assetClass 추론, 근거 제시형 식별자

신경망은 0개가 되고, 남는 것은 12.9MB OCR 모델뿐이다.

## 3. Stage A1 실측 (Orin, onnxruntime **CPU**)

엔진: RapidOCR PP-OCRv5 `korean` rec(12.86MB) + PP-OCRv6 det. 채점: 기존 `parity.py --no-llm`.

**속도 — 8장 11.3s (1.4s/장).** 대조: 같은 8장이 VLM(`3b-ft3-q8`)으로 Orin **GPU** 13.9s/장 = 111s.
CPU에서 이미 4자리수 빠르므로 가속기가 필요 없다.

**정확도(GT 31종목) — 판정 PASS ✅**

| 필드 | 결과 | |
|---|---|---|
| 재현율 / 환각 | **31/31** ✅ / **0** ✅ | |
| value · qty · cost | **31/31** ✅ | 금액 자릿수·쉼표·부호 정확, 회계 항등식 전 행 성립 |
| broker · accountType | **31/31** ✅ | |
| qty_src · price_src | **31/31** ✅ | 출처 범주까지 일치 |
| 게이트 | **침묵** ✅ | 정상 입력에 경고 0건 |
| name / price | 29/31 | 잔여 2건 — 아래 |

**컨트롤 4종(음성 대조)**: 화면 누락·빈 화면·환각행 주입 → **전부 경고** / 순서 셔플 → **동일 결과** ✅

**잔여 2건은 둘 다 OCR 품질이고 바인더 로직이 아니다** — T1의 실제 실패 모드다:
- `IVV` → **`IWV`** (conf 0.98, 3x 확대에도 동일). 같은 글꼴에서 `VV`와 `W`는 사실상 구분 불가.
  하필 `IWV`도 **실재하는 ETF**라 심볼 해석에 성공해 조용히 다른 종목이 된다.
- `알파벳 A` → `알파벳A` (공백 유실) → Naver 자동완성 실패로 GOOGL 미해석 → 주가가 원화로 남음.
  (`알파벳 A`는 정상 해석된다 — 공백 하나 차이)

→ **T1의 실패 모드는 '확신에 찬 글리프 혼동'이다.** 값은 정확한데 **식별자**가 틀린다.
이 빈칸을 메우는 게 T2(교차검증·표기 정규화)의 존재 이유다.

### 결정적 발견 — 방향 분류기가 오류의 원인이었다

RapidOCR의 각도 분류기(cls)가 **단어마다** 180° 회전을 독립 판정하는데 스크린샷에서 오판한다.

| | cls ON | cls OFF | 수동 180° 회전 |
|---|---|---|---|
| 엔비디아 | `'{이그A'` c=0.41 | **`'엔비디아'` c=1.00** | `'{이그A'` c=0.41 |
| 팔란티어 테크 | 박스 자체 소실 | **`'팔란티어 테크'` c=0.96** | `'티이ㅋ'` c=0.68 |

수동 회전이 실패 시그니처를 그대로 재현한다 → 기전 확정. 크롭·2x확대·패딩·리샘플은 전부 무효
(스케일 불변 실패)였고, PP-OCRv4 korean·중국어 모델도 같이 실패했다. 스크린샷은 회전이 없다는
불변식이 절대적이므로 **단계 자체를 끈다**(임계값으로 덮지 않는다). 부수적으로 cls가 조용히
망가뜨리던 다른 박스들도 살아났다(`보유계좌 상품별 자산현황`, `실시간지연`).

교훈: `[[parity-is-knife-edge]]`의 반대 사례 — 실패가 모델 한계처럼 보였지만 **파이프라인
단계 하나**였다(`[[extraction-failures-are-pipeline-bugs]]`가 OCR 경로에서도 성립).

## 4. Track B 실측 — 사다리의 나머지 칸을 채운다

### 4.1 T2 역량 실측 — rung은 **1B와 4B 사이**에 있다

탐침: `eval/harness/probe_t2.py`(고정·재현 가능, `temperature:0`). A1에서 **실제로 실패한** 5개
케이스를 그대로 질의. 격리 인스턴스 `:11435` + 전용 모델 스토어.

| 과제 | 1B 답 | 4B 답 | 정답 |
|---|---|---|---|
| assetClass `ACE 엔비디아밸류체인액티브` | 채권 | **성장주** ✅ | 성장주 |
| assetClass `TIGER 차이나휴머노이드로봇` | 채권 | **성장주** ✅ | 성장주 |
| 티커 교정 (`IWV`, 단가 $751 / IVV=$751·IWV=$390 **프롬프트에 제시**) | IWV | **IVV** ✅ | IVV |
| `알파벳A` → 티커 | AAPL | **GOOGL** ✅ | GOOGL |
| | **0/4** | **4/4** | |
| *(제외)* broker `Super365` → 정규명 | *`Super365`* | *`슈퍼리츠`* | *메리츠증권* |

> **`Super365` 건은 채점에서 뺐다.** 이건 검색으로만 알 수 있는 사실이라 **모델 크기와 무관**
> 하다 — 어느 티어든 외부 근거(웹검색·캐시)가 있어야 풀린다. 모델의 실패로 적으면 채점이
> 틀린다. 다만 *답하는 방식*은 여전히 기록해둘 값어치가 있다: 둘 다 '모르면 모름'을 지시했는데
> 4B는 실재하지 않는 `슈퍼리츠`를 지어냈다.

**1B = 0/4, 그리고 위험하다.** 티커 교정은 판단 근거를 프롬프트에 그대로 줬는데도 틀렸다 —
지식 부족이 아니라 **주어진 제약을 따르지 못하는 수준**이다. `알파벳A → AAPL`은 확신에 찬
환각이다. 이 레포의 가치가 '근거 없으면 답하지 않는다'는 게이트인데 1B는 **근거 없이 답하는
부품**이다 — 빈칸을 메우기는커녕 오염원이 된다. **순손실.**

**4B = 4/4. rung은 실재한다.** 4B는 T1이 비운 칸을 실제로 닫는다 — assetClass 추론,
그리고 **독립 근거(시세)를 준** 식별자 교정.

그래도 **게이트 뒤에 둬야 한다.** 근거가 없을 때의 실패 방식이 여전히 환각이기 때문이다
(`슈퍼리츠` — 실재하지 않는 회사명, '모르면 모름'을 명시했는데도). 4B의 답은 **제안**이지
근거가 아니다. 쓸 수 있는 자리는 (a) `assetClass` 키워드 표가 못 맞춘 신규 상품명,
(b) 시세로 교차검증 가능한 식별자 교정 — 둘 다 틀려도 결정론 게이트가 잡는 자리다.

**크기(3.3GB, Q4_K_M)는 기각 사유가 아니다.** base 모듈 200MB를 넘어 Play Asset Delivery가
필요하지만, 그건 모델을 쓰는 모든 티어에 똑같이 걸리는 절차다. 부대비용으로만 적는다.

**주의 — T2 런타임은 아직 미측정이다.** 위 지연(2~8s)은 **Orin GPU**의 ollama 수치이고 S23이
아니다. LiteRT-LM은 Android Kotlin API라 폰 지연·메모리는 A3와 같은 툴체인으로만 잰다.

### 4.2 T3 실측 — 배포 가능한 크기의 **범용** VLM은 표를 못 읽는다

`gemma3:4b`는 vision 지원 VLM이고 3.3GB라 T3' (4.63GB)와 달리 4GB 한도 **안**이다. 그래서
"커스텀 FT 없이, 배포 가능한 크기로 (i)(iv)가 되는가"를 직접 물을 수 있다. 프로덕션과 **동일
프롬프트**(`prompt4f.txt`)·동일 하네스로 2장 실행:

| 화면 | 4B가 낸 broker | 4B가 낸 종목명 | 실제(GT) |
|---|---|---|---|
| SMART 160139 | `미래에셋증권` | 국내주식/해외주식/원화예수금… | 메리츠증권 |
| mPOP 160333 | `KOSDAQ` | **`△△전자`** | 삼성증권 |

**전면 날조다.** GT의 broker는 `메리츠증권`·`삼성증권` 둘뿐인데 4B는 화면에 없는 증권사를 냈고,
`△△전자`는 회사명이 아니라 **가림 기호 자리표시자**다. 그런데 출력은 **문법적으로 완벽한 JSON**
(11칸 정확, 자산군·통화까지 그럴듯)이라 파서를 그대로 통과한다 — 가장 위험한 실패 방식이다.

→ **T3 rung은 3.3GB 범용 VLM에 없다 — 날조는 기각 사유다.** 정리하면:

| | 표를 읽을 수 있나 | 폰에서 도는 속도인가 |
|---|---|---|
| 범용 VLM 4B | ❌ **날조** | (무의미) |
| 커스텀 FT VLM | ✅ | ❌ **739~957s/장**(§4.3) |
| **OCR + 기하** | ✅ | ✅ **1.4s/장** |

정확도와 **엣지 실행성**을 동시에 갖는 칸은 T1 하나뿐이다. 그리고 §1의 제약 때문에 두 셀을
합칠 방법이 없다 — 커스텀 FT 가중치는 플랫폼 가속기(ML Kit·LiteRT-LM)가 받지 않으므로
범용 런타임으로 내려와야 하고, 거기엔 가속기가 없다.

**주의:** 이 판정은 크기가 아니라 **날조와 속도**로 내린 것이다. Asset Delivery는 어느
모델에나 붙는 절차라 기각 근거로 쓰지 않았다.

### 4.3 T3' 상한 실측 — 폰 CPU 경로는 **500배 느리다**

`num_gpu:0` + `taskset -c 0-5`로 `3b-ft3-q8`을 Orin **CPU**에서 실행(격리 인스턴스 `:11435`).

| 화면 | 소요 |
|---|---|
| 160139 | **739.0s** |
| 160155 | **956.8s** |
| (n=2에서 중단 — 자릿수 판정에 충분) | |

**Orin CPU는 S23의 낙관적 상한이다**(대역폭 204GB/s vs ~68GB/s, 코어도 많다). 즉 실제 폰은
이보다 **확정적으로 느리다**. 8장이면 Orin CPU에서도 1.7~2시간이다.

대조: 같은 8장이 **OCR+기하로 11.3초**(1.4s/장). **약 500~700배.**
사전 산수 추정(10~30분/장)이 실측으로 확인됐다 — T3'는 정확도가 아니라 **속도로 죽는다.**

### 4.4 T1의 다양성 실측 — 값은 버티고, **근거 없는 칸에서 지어낸다**

A1 파리티는 픽스처 8장(캡처일 2026-07-09) 하나에만 걸려 있었다. 다른 날 캡처한 `test-asset`
8장(2026-07-21, 같은 두 앱·**다른 포트폴리오 상태**)으로 같은 파이프라인을 돌렸다.
정답 데이터가 없으므로 손으로 라벨링하는 대신 **레포 자신의 불변식**으로 채점한다.

| | 결과 |
|---|---|
| 추출 | 8장 → **34종목 / 39.4초** |
| 회계 항등식 `value = cost + pnl` | **위반 0건** ✅ |
| 게이트 경고 | **0건**(침묵) |
| broker | 28행 정상(메리츠 19·삼성 9) / **6행이 계좌번호** ❌ |

**값 축은 버틴다** — 다른 날, 다른 종목 구성, 다른 금액에서도 자릿수·부호·항등식이 전부 성립한다.
`[[testasset-diagnosis-phase2]]`의 값-강건성 결론이 OCR 경로에서도 재현됐다(과적합 아님).

**깨지는 축은 broker다.** 6행의 broker가 `1234567890-14[ISA(평생혜택 중개형)(비대면)]` 처럼
**계좌번호**다. 기전을 끝까지 확인했다:

| 캡처 | mPOP 화면 구성 | 결과 |
|---|---|---|
| 07-09(픽스처) | `종합잔고` 화면 상단에 **`삼성증권`** + 계좌번호 목록 | 상속 성공 → broker 31/31 |
| 07-21(test-asset) | 계좌별 `종합잔고` 4장만. **어느 화면에도 증권사명이 없다** | 상속 출처 없음 → **계좌번호가 broker가 됨** |

즉 **OCR이 놓친 게 아니다** — 화면에 정말 없다. 문제는 그다음이다:

> `finalize.py:277` `h["broker"] = broker or label or None`
> 해석에 실패하면 **화면 라벨(=계좌번호)로 폴백**한다. 그리고 게이트는 **침묵한다.**

이건 '근거 없으면 답하지 않는다'는 이 레포의 원칙을 정면으로 어긴다. 값이 아니라 **라벨을
지어내는** 것이고, §4.2에서 범용 VLM을 기각한 이유(날조)와 **같은 종류의 실패**다 —
규모만 작을 뿐이다. 올바른 동작은 broker를 비우고 **경고를 올리는 것**이다.

**그리고 이건 T1의 결함이 아니다.** `finalize.py`는 비전 LLM 경로와 **공유**한다 —
VLM이 같은 화면을 봐도 화면에 없는 증권사명을 만들어낼 수는 없으므로 동일하게 폴백한다.
§5의 게이트 순서 결함과 같은 성격(**OCR이 드러냈을 뿐, 파이프라인의 결함**)이다.
공유 코드 변경이라 **머지 전 승인 필요.**

### 4.5 새 화면 폼 — `전체계좌` 목록(행마다 계좌 구분자)

실사용 업로드에서 **처음 보는 화면 폼**이 들어왔다(2026-07-31, `captures/20260731T085311Z_792d11`).
`보유계좌 상품별 자산현황 > 전체계좌` — 세로 **4928px**·**2870px**짜리 스크롤 이어붙인 캡처이고,
종목마다 **그 위에 계좌 라벨이 다시 찍힌다**:

```
y=1128  '1234-5678-01(Super365)'   ← 계좌 구분자(행 머리)
y=1192  'AIPO'
y=1277  '110주'      '4,579,671원'
y=1356  '-743,649원' '-13.97%'
y=1508  '1234-5678-01(Super365)'   ← 다음 블록
```

**초기 결과: 값 15/15 정확, broker 15/15 `None`.** 원인은 `bind.rows_from_list`의
'같은 문구가 반복되면 UI 크롬' 필터였다. 계좌 라벨이 10회 반복되니 `이체`·`거래내역` 같은
크롬으로 취급돼 버려졌다. **규칙 자체는 맞다**(반복 = 행 이름 아님) — 틀린 건 *버린* 것이다.
계좌 라벨은 행 이름이 아니라 **행 그룹의 머리**다.

수정: 반복 라벨 중 `F.acct_tokens`가 있는 것을 **구분자로 분리**하고, 각 행의 broker를
'바로 위의 구분자'로 준다(위에 없으면 `None` — 지어내지 않는다). accountType도 같은 출처.
정규화는 여전히 `resolve_broker`가 한다(단일 출처).

**결과: broker 15/15 `메리츠증권`.** 검색도 LLM도 쓰지 않았다 —
`resolve_broker('1234-5678-01(Super365)', use_llm=False)`가 캐시의 `super365`로 바로 푼다.
**A1 파리티 회귀 없음**(31/31 · 환각 0 · 게이트 침묵 · 컨트롤 4종).

#### 이 화면이 드러낸 것 두 가지

**① 독립 검증 성공.** img1의 상세합 **119,148,155원**이 화면 상단 `평가금액`
**119,148,155원**과 **원 단위까지 일치**한다. 정답 라벨 없이도 T1이 4928px 스크롤 캡처를
정확히 읽었다는 독립 근거다.

**② 게이트의 사각지대(오경보).** 그런데도 img1에 `상세합 — 근접 총액 없음` 경고가 떴다.
게이트는 총액 후보를 **계좌요약 화면의 행**에서만 모으는데, 이 폼은 총액이 **같은 화면 상단**에
있고 그 자리는 `평가금액`이라 `_is_field_label`이 행에서 제외한다 → 맞춰볼 근거를 못 본다.
즉 **화면에 답이 있는데 게이트가 안 본다.** (수정은 `finalize.py` 총액 수집 범위 — 공유 코드라 승인 대상.)

**③ 그리고 참 양성도 잡았다.** img2는 상세합 33,138,050 vs 화면 총액 34,963,650 —
**1,825,600원 부족**. 확인해보니 캡처가 잘려 있었다(구분자 5개 = 추출 5행, 이미지가 2870px에서 끝).
게이트가 **불완전한 캡처를 정확히 잡아냈다.**

#### 여러 계좌가 섞이면 계좌별로 갈리는가 — 잰다 (`eval/harness/probe_multiacct.py`)

실제 업로드는 계좌 하나뿐이라 그것만으로는 답할 수 없다. **실제 img1의 OCR 박스를 그대로 쓰고
구분자 텍스트만 바꿔** 기하 로직만 시험한다(좌표·줄 구조·금액 배치는 손대지 않는다).

| 시나리오 | 결과 |
|---|---|
| 두 계좌 5:5 | ✅ 5/5 정확히 분리 |
| 교대 A/B/A/B | ✅ 10행 전부 정확 |
| **한 계좌에 종목 1개** | ✅ 9:1 정확 (수정 후) |

세 번째가 처음엔 **깨졌다**. 구분자를 `반복 2회 이상 + 계좌토큰`으로 잡았는데 종목이 하나뿐인
계좌는 라벨이 1회만 나와 안 걸렸고, 그 라벨이 **종목명 행으로 둔갑해** 아래 행의 손익을 훔쳤다
(가짜 행 `value=-1,633,630`, 행 수 10→11, 다음 종목의 계좌도 오배정).

두 번째 시도(`아래 한 행 안에 종목명이 있으면 구분자`)는 **A1을 깨뜨렸다** — 계좌요약 화면도
계좌 라벨 아래 UI 라벨이 있어 같이 걸렸다(160333: 3행→2행, 이름이 `상품구성`·`계좌현황`,
broker 27/31 **FAIL**).

답은 두 폼의 **실측 기하**에 있었다 — 계좌 라벨에서 아래로 내려갈 때 무엇이 먼저 오는가:

| | 계좌 라벨 아래 첫 요소 |
|---|---|
| 계좌요약(160333) | y=579 라벨 → y=665 **금액 `5원`** (자기 값, 사이에 이름 없음) |
| 전체계좌(img1) | y=1128 라벨 → y=1192 **이름 `AIPO`** → y=1304 금액 |

→ **계좌 라벨과 그 아래 첫 금액 사이에 종목명이 끼면 구분자**, 금액이 먼저 오면 그 라벨 자신이
행이다. 상수 없이 두 폼을 가른다. **A1 파리티 PASS 복구**(broker 31/31·게이트 침묵·컨트롤 4종).

교훈: 규칙을 추측으로 두 번 바꿨고 두 번 다 틀렸다. 세 번째에 **두 폼의 기하를 나란히 재고 나서야**
상수 없는 판별자가 나왔다 — `[[extraction-failures-are-pipeline-bugs]]`와 같은 결.

### 4.6 오버피팅 점검 — held-out에서 갈린다

`bind.py`는 픽스처 8장을 보며 만들었다. **그래서 픽스처 성적은 증거가 못 된다.**
`bind.py` 완성 **이후에** 들어온 데이터만 본다.

| held-out | 내용 | 결과 |
|---|---|---|
| `test-asset` 8장 (07-21) | 같은 앱, **다른 포트폴리오 상태** | 34행 · 회계 항등식 위반 0 · 게이트 침묵 / **broker 6행 오류** |
| 실사용 업로드 2장 (07-31) | **처음 보는 화면 폼**(전체계좌, 4928px 스크롤) | 값 15/15 정확(**수정 전에**) / **broker 15/15 None** |

#### 기존 VLM과의 정면 비교 — 같은 held-out, 순환논증 없는 심판

정답 라벨이 없으므로 **화면에 찍힌 총액**을 심판으로 쓴다(양쪽 다 모르는 독립 근거).

| img1 (4928px, 화면에 10종목) | 행 | 평가금액 합 | 차이 |
|---|---|---|---|
| 화면 `평가금액` | — | 119,148,155 | — |
| **OCR + 기하** | **10** | 119,148,155 | **+0** |
| VLM `3b-ft3-q8`(프로덕션 동일 조건) | 9 | 117,176,385 | **−1,971,770** |

VLM이 마지막 행 `Voo`를 통째로 빠뜨렸고 부족분이 정확히 그 행의 평가금액이다.
img2(짧은 쪽)는 양쪽 다 5행 정확 — 즉 **VLM은 긴 화면에서 행을 잃는다**(절반 리샘플 후에도
2464px). 그리고 §4.5의 게이트 사각지대 때문에 **이 누락은 경고 없이 지나간다.**

#### 오버피팅 지표 (정량)

| | |
|---|---|
| `bind.py` | 518줄 |
| 특정 화면을 보고 쓴 규칙(`측정` 주석) | **13개** — 이 중 `160333` 하나가 **6개**를 낳았다 |
| 튜닝 상수 | 약 10개, **전부 상대값**(`width*0.5`, `med_h*2`, `pitch*0.60`) |
| 절대 픽셀 좌표 · 종목명 하드코딩 · 앱별 분기 | **0** |

**위험은 실재한다** — 규칙 13개가 각각 특정 화면을 보고 쓰였다. 다만 상수가 전부 해상도·글리프
높이·행 피치에 **상대적**이라 해상도와 레이아웃 스케일에는 자동으로 따라간다.

#### 결론 — 무엇이 일반화하고 무엇이 안 하는가

> **값은 일반화한다. 라벨은 안 한다.**
>
> 값은 **기하 불변식**에서 나온다(라벨이 최근접 금액을 소유, 같은 밴드의 y순서 = 헤더 순서).
> 이 불변식은 폼이 바뀌어도 유지된다 — 그래서 처음 보는 화면에서 15/15가 **수정 전에** 맞았다.
> broker는 **앱별 관례**에서 나온다(어디에 적히는지, 대괄호인지 괄호인지, 아예 없는지).
> 폼마다 다르므로 **새 폼마다 깨진다.** 실제로 held-out 두 건 다 broker에서만 틀렸다.

그래서 **확장성의 열쇠는 바인더 규칙을 늘리는 게 아니다.** 앱 폼은 열거할 수 없다.
열거할 수 있는 건 "**근거가 화면에 없다**"는 상태 하나뿐이고, 그건 폼과 무관한 성질이다.
→ `finalize.py`의 폴백 제거(§4.4)와 총액 인식 확장(§4.5)이 규칙 추가보다 우선한다.
지금은 근거가 없을 때 **계좌번호를 지어내고 게이트가 침묵**하는데, 이게 확장성의 진짜 병목이다.

**표본이 작다는 것도 그대로 적는다.** 앱 **2종**·화면 폼 **4종**이 전부다. 오늘 만든 구분자
규칙도 폼 **2종**의 기하에서 나왔다 — 3번째 폼에서 깨질 수 있다.
'다른 증권사 앱 폼'은 `[[testasset-diagnosis-phase2]]`가 기록한 한계 그대로 열려 있다.

## 4.7 공유 게이트 수정 2건 (승인 후 반영)

`finalize.py`는 OCR·VLM 두 경로가 **공유**한다. 두 결함 모두 T1의 결함이 아니라 파이프라인의
결함이었다(§4.4·§4.5).

**① broker 폴백 제거 — 지어내지 말고 비우고 경고한다.**
`h["broker"] = broker or label or None`에서 `or label`을 뺐다. 그 라벨은 대개 계좌번호라
`broker='1234567890-14[ISA(...)]'` 같은 값이 나왔고 게이트는 침묵했다. 이제 비우고
`증권사 미상 — 화면에 근거 없음` 경고를 낸다(owner 추론이 끝난 뒤에 판정해야 거짓 경보가 없다).

**② 화면 자신의 총액을 대조 근거로 쓴다.**
전체계좌 폼처럼 계좌요약 화면이 함께 올라오지 않으면 게이트는 대조할 총액이 없어
`근접 총액 없음`이라는 **같은 문구**를 정확한 화면과 누락된 화면에 똑같이 냈다.
추출기가 화면의 `평가금액` 총액을 예약행(`finalize.SCREEN_TOTAL`)으로 넘기고, `_cross_check`가
이를 **추가** 검사로 쓴다(대체하면 요약총액이 소비되지 않아 '미대조' 거짓 경보가 난다 — 실측).
VLM 경로는 이 행을 내지 않으므로 동작이 바뀌지 않는다.

| held-out | 수정 전 | 수정 후 |
|---|---|---|
| 실캡처 broker | 15/15 `None` | **15/15 메리츠증권** |
| 실캡처 경고 | `근접 총액 없음` ×2 (정확/누락 구분 못 함) | **img1 침묵, img2 `-1,825,600 행 누락 의심`** |
| `test-asset` broker | **계좌번호 6행(날조)** | `None` 6행 + **미상 경고 3건** |
| A1 파리티(OCR) | PASS | **PASS 유지**(31/31·게이트 침묵·컨트롤 4종) |

### 부수 관찰 — 프로덕션 VLM이 오늘 재실행에서 파리티 FAIL

공유 코드 회귀를 확인하려고 `3b-ft3-q8`로 8장을 새로 돌렸다(NP=1, prompt4f).

| | |
|---|---|
| broker | **27/31** — `한화오션` 등 3행이 `한국투자증권` |
| qty·price | 30/31 — `TIGER 미국나스닥100` 30→100 |
| 게이트 | **경고 0건(침묵)** |

`한국투자증권`은 **모델이 raw JSON에 직접 낸 값**이다 — 그 화면엔 계좌번호뿐이고 어떤 증권사명도
없다. 즉 **VLM이 증권사를 지어냈다.**

**내 수정과 무관함을 증명했다**: 수정 전 커밋(`f93ee35`)의 `finalize.py`로 **같은 raw**를 채점해
결과가 완전히 동일했다(27/31·같은 문자열·같은 FAIL). 폴백 제거는 값을 `None`으로 만들 뿐
다른 값으로 바꿀 수 없다.

**NP=2 재실행 — 정정.** 위에서 'knife-edge, NP 차이일 수 있다'고 적었던 것은 **틀렸다.**
프로덕션 설정(NP=2)으로 다시 돌리니 **완전히 동일하게 재현**된다. raw 8장 중 7장이 바이트 단위로
같고, 다른 1장도 `price`·`cost` 끝자리만 다르며 **실패 항목은 양쪽 동일**하다.
불안정이 아니라 **안정적·재현되는 FAIL**이다.

#### 그리고 A/B로 원인이 둘로 갈렸다 (`main` vs 스파이크, **같은 raw**)

| | `main`(스파이크 전) | 스파이크(현재) |
|---|---|---|
| broker | 27/31 ❌ `한국투자증권` | 27/31 ❌ **동일** |
| qty · price · qty_src | **31/31 ✅** | **30/31 ❌** |

- **`한국투자증권`은 `main`에서도 FAIL** → 이 스파이크와 무관한 **기존 결함**이다(모델의 날조).
- **`TIGER 미국나스닥100` 수량 회귀는 이 스파이크가 만든 것**이다 — §5의 게이트 순서 변경.

기전(추적 확인):

```
qty=100                 ← VLM이 이름 속 '100'을 수량으로 오독(레포에 기록된 실패 모드)
symbol_note: 심볼 불일치 — 133690.KS 종가로 화면 단가(58,884)가 설명되지 않음
symbol=None             ← 심볼 게이트가 먼저 돌며 심볼을 떨군다
qty_src='screen'        ← 수량 게이트가 symbol 없는 행을 건너뛴다 → 오독 수량 100이 생존
```

> **두 게이트가 서로를 필요로 한다.** 심볼 게이트는 `value/qty`를 쓰니 qty가 맞아야 하고,
> 수량 게이트는 심볼의 참가격을 쓰니 심볼이 맞아야 한다. 순서를 바꾼 것은 **어느 쪽이 깨질지를
> 바꿨을 뿐** 순환을 없애지 못했다 — 원인을 구조적으로 제거하지 않고 순서로 때운 결과다.

#### 구조적 해법 — 적용·검증 완료

**폐기한 1안: '`value/참종가`가 정수면 심볼이 맞다'.** 실측에서 **분별력이 없었다** —
오독 티커 `IWV`가 **58.02주(잔차 0.02)** 를 내서 정답 `IVV`의 33.06주(잔차 0.06)보다 오히려
더 정수에 가까웠다. 수량이 크면 시세가 0.4%만 움직여도 소수부가 한 바퀴 돌기 때문에
애초에 심볼 판별에 쓸 수 있는 신호가 아니다(233주면 0.43%).

**채택안: 오염된 수량으로는 심볼을 판정하지 않는다.**
`_qty_from_name(h)` — 화면 수량이 **종목명 속 숫자와 같은가**. 열 오매핑의 대표 실패 모드이고
(`TIGER 미국나스닥100`→100, `KODEX 미국S&P500`→500) **심볼·시세를 전혀 쓰지 않으므로** 순환을 끊는다.
오탐 검증: 픽스처 31행 중 이름에 숫자가 있는 4행 모두 정답 수량이 그 숫자와 다르다
(S&P500→115·312, 나스닥100→30, 나스닥100…50→223) — **오탐 0**.

행 단위 추적 — **각 행을 정확히 하나의 게이트만 처리한다**(그래서 순서가 결과를 바꿀 수 없다):

| 행 | 심볼 게이트 | 수량 게이트 | 결과 |
|---|---|---|---|
| `IWV`(오독 티커) | 심볼 기각 | 건너뜀(symbol 없음) | qty **33 screen 보존** ✅ |
| `TIGER 미국나스닥100` | **판정 포기**(이름숫자 오염) | 100 기각 | qty **30 capture-close** ✅ |
| 정상 `IVV` | 통과 | 통과 | 화면값 유지 ✅ |

**검증 결과**

| | OCR 경로 | VLM 경로 |
|---|---|---|
| qty · qty_src | **31/31** ✅ | **31/31** ✅ (`main`과 동일) |
| price_src | **31/31** ✅ | 20/31 (`main`과 동일) |
| 판정 | **PASS ✅** (컨트롤 4종 정상) | FAIL — 잔여는 전부 `main`에도 있는 기존 결함 |

**남은 구멍(정직하게):** 수량이 이름숫자로 오염**되고 동시에** 심볼도 틀린 행은 여전히
잘못 처리된다 — 심볼 게이트가 포기한 사이 수량 게이트가 틀린 심볼의 시세로 수량을 유도한다.
두 오류가 한 행에 겹쳐야 하므로 드물지만, 구조적으로 남아 있다.

두 가지를 그대로 적어둔다:
- **수정 ①은 우리가 지어내는 것을 막지만 모델이 지어내는 것은 못 막는다.** VLM이 정규명을
  뱉으면 `resolve_broker`가 그대로 채택한다. 그리고 이 경우 **게이트는 침묵한다** — 금액은
  맞으므로 총액 대조에 걸리지 않는다. 남은 구멍이다.

## 4.8 ML Kit 박스 단위 위험 — 폰 없이 봉투를 쟀다

A3의 유일한 미검증 위험이었다. `bind._amount_of`는 화면이 금액과 수익률을 **한 박스에**
담는다고 전제하는데(`-2,054,000원|-13.54%`), ML Kit은 Block > Line > Element 계층이라 박스
경계가 다르다. 깨지면 손익이 통째로 사라져 회계 항등식이 무너진다. "기기 없이는 확인 불가"로
적어뒀지만, **확인할 수 없는 것은 ML Kit의 실제 그룹핑이고 확인할 수 있는 것은 bind.py가
견디는 그룹핑의 범위**다. 후자를 쟀다.

방법(`eval/harness/mlkit_sim.py`): ML Kit이 Element를 만든 뒤 Line으로 묶는 순서를 그대로
흉내낸다 — RapidOCR 박스를 공백 토큰으로 쪼갠 뒤(=Element), 같은 줄에서 가로 간격이
`R × 글자높이` 이하인 것을 다시 합친다(=Line). **R 하나가 element(R→0)에서 block(R→∞)까지를
잇는 단조 노브**다. 병합 코드는 프로덕션(`ocr.merge_lines`)을 **그대로 import** 한다 — 사본을
두면 여기서 잰 봉투가 기기에서 도는 코드의 봉투라는 보장이 사라진다.

먼저 실제 간격 분포를 쟀다(픽스처 8장, 간격/글자높이):

| p10 | p25 | p50 | p75 | p90 | p99 |
|---|---|---|---|---|---|
| 0.35 | 0.42 | 1.49 | 5.43 | 9.45 | 19.91 |

**이봉 분포**다 — 구절 안의 공백은 0.35~0.6, 열 사이는 2.7~10. 그 사이가 계곡이다.

파리티 스윕(`parity.py --no-llm`, 동일 채점기):

| R | 재현율 | 판정 | 깨지는 방식 |
|---|---|---|---|
| element(병합 없음) | 29/31 | **FAIL** | broker 13/29 — 라벨이 낱말로 쪼개져 계좌 구분자를 못 만든다 |
| 0.4 | 30/31 | FAIL | 과소병합 — 구절이 안 붙는다 |
| 0.5 | 31/31 | FAIL | qty_src 30/31 |
| **0.6 · 0.8 · 1.0 · 1.2 · 1.5 · 1.8** | **31/31** | **PASS ✅** | — |
| 2.0 | 31/31 | FAIL | 과대병합 — 열이 융합(`-12.95% 6,421,430`) |

**봉투는 R ∈ [0.6, 1.8]**이고 양쪽 밖은 각각 다른 방식으로 죽는다. 양성 대조군이 존재한다는
것이 중요하다 — 중간 R에서 PASS가 나오므로 시뮬레이터가 고장난 게 아니다.

> **실제로 첫 스윕은 R=0.5~3.0에서 똑같이 FAIL했다.** R을 6배 바꿔도 결과가 같은 건 물리적으로
> 이상해서 bind.py가 아니라 시뮬레이터를 의심했고, 맞았다: 줄 묶기를 이웃끼리 이어붙이는
> 방식으로 짜서 서로 다른 줄이 한 줄로 이어졌고, 그러면 x가 겹쳐 **간격이 음수가 되어 R과
> 무관하게 무조건 병합**됐다. 대표값 기준으로 고치자 R 의존성이 살아났다. 이 버그를 그대로
> 뒀다면 "ML Kit 경로는 못 쓴다"는 **틀린 결론**을 냈을 것이다.

**채택한 대응 — 박스 단위를 우리 손으로 가져온다.** `OCR_MLKIT_GRANULARITY` 기본값을
`line` → **`element`** 로 바꾸고, `ocr.merge_lines(boxes, OCR_LINE_MERGE=1.0)`로 우리가 합친다.
ML Kit의 Line 그룹핑이 봉투 안에 드는지는 **우리가 정할 수 없는 값**이지만, 우리 임계값은
봉투 한가운데 있음을 보증할 수 있다. 기기에서 할 일이 "파리티를 처음부터 다시 받는다"에서
**"실제 간격 분포가 봉투 안인지 확인한다"**로 좁아졌다.

**한계(정직하게):** 이건 근사다. 깨지면 결론적이고(전제 의존이 증명된다), 통과는 약한 증거다 —
실제 ML Kit Element가 우리 공백 분해와 다르게 잘릴 수 있다. 기기 검증은 여전히 필요하다.

## 4.9 라벨의 독립 심판 — 모델의 날조를 게이트가 잡는다

§4.7에 미해결로 남겨둔 결함이다. **값에는 '총액'이라는 독립 심판이 있어서 틀리면 게이트가
운다. 라벨에는 없었다** — 그래서 비전 모델이 `한국투자증권`을 지어내도 금액만 맞으면 총액
대조를 통과하고 게이트는 침묵했다(`main`에서도 재현되는 기존 결함).

**심판을 만들 재료가 생겼다.** OCR 텍스트는 비전 모델과 **독립**이고 1.4s면 나온다. 화면의
OCR 원문을 `evidence`로 finalize에 넘겨, 모델이 주장한 증권사명이 화면에 실재하는지 본다
(`finalize._label_supported`). 근거가 없으면 비우고 경고한다 — §4.7에서 **우리 폴백**에 적용한
'근거 없으면 비운다' 규칙을 이번엔 **모델 출력**에 적용하는 것이다.

A/B(`EVIDENCE=0|1`, VLM `qwen2.5vl:3b-ft3-q8` np2 결과, 같은 채점기):

| | 심판 없음(기존) | **심판 있음** |
|---|---|---|
| broker | **27/31 ❌** `한화오션` 등 3행이 `한국투자증권` | **31/31 ✅** |
| 게이트 | **0건 — 침묵** | 1건 — `'한국투자증권' 근거 없음(지어낸 값으로 판단해 비움)` |
| 판정 | **FAIL** | **PASS ✅** |

broker가 27/31 → **31/31로 올라간** 이유가 흥미롭다. 날조된 값이 비워지자 **원래 설계돼 있던
계좌요약 화면으로부터의 상속이 비로소 동작했다** — 날조가 정답을 덮고 있었던 것이다.

**false positive 하나를 실측으로 잡았다.** 처음엔 `삼성증권`도 "근거 없음"으로 찍혔는데, 화면이
좁아 OCR이 `현금성자산(삼성증` … `3,065,859` `0` … `권)`으로 줄바꿈해 읽었기 때문이다. 끼어든
것은 **다른 열의 금액**이지 텍스트가 아니므로, 숫자 토큰을 뺀 형태도 함께 대조하도록 고쳤다
(`_ev_forms`). 수정 후 경고는 진짜 날조 1건만 남는다.

**자기점검:** OCR 추출 경로에서는 broker가 화면 텍스트에서 나오므로 이 심판이 **항상 통과**해야
한다 — 실제로 OCR 파리티는 게이트 침묵을 유지한 채 PASS다. 심판이 무해함이 확인된다.

**비용:** VLM 경로에 화면당 OCR 1.4s가 붙는다(Orin 13.9s/장 대비). OCR 경로는 이미 만든 박스를
재사용하므로 **0**이다. `evidence`가 없으면 판정하지 않는다(무판정이지 통과가 아니다) — 옛
호출부와 호환된다.

## 4.10 기기가 다르면 — 해상도·폭·종목 수

픽스처 8장은 **전부 1080폭**이다. 다른 기기(S23 Ultra 1440폭, 폴더블, 글꼴 크기 설정)에서도
되는지는 재본 적이 없었다. 기기별 분기는 기기 목록을 영원히 쫓는 길이라, **화면이 자기 단위를
스스로 내게** 만드는 쪽으로 갔다.

먼저 잰다(`eval/harness/device_sim.py` — 박스 좌표만 변환해 bind를 OCR과 분리):

| 축 | 실제로 달라지는 것 | 수정 전 | 수정 후 |
|---|---|---|---|
| 해상도(DPI) | 위치·크기·글자높이가 **전부 비례** | **1.333배에서 FAIL** (재현율 27/31) | **0.5 ~ 3.0배 PASS ✅** |
| 화면 폭 | 글자 크기는 그대로, **열만 벌어진다** | **2.0배에서 FAIL** (헤더 화면 0행) | **0.8 ~ 3.0배 PASS ✅** |
| 행 간격 | 줄 **사이** 간격만 달라진다 | 1.5배 FAIL | **0.75 ~ 3.0배 PASS ✅** (§4.11에서 완결) |
| 종목 수 | 화면이 길어진다 | — | **×32(288행)까지 회계 항등식 위반 0** |

### 무엇이 문제였나 — 절대 픽셀은 사실 '글자 높이'였다

`bind.py`에 `90`·`120`·`70` 세 상수와 `width=1080` **기본값**이 있었고, **호출부는 아무도 폭을
넘기지 않았다** — 어떤 기기의 화면이든 1080폭으로 간주됐다. 픽스처에서 세 상수를 글자 높이로
나눠보니 각각 **1.7 · 2.2 · 1.3배로 일정**했다. 원래 글자 높이였던 것을 픽셀로 적어둔 것이다.

수정은 세 겹이고, 뒤로 갈수록 상수가 사라진다:

1. **`metrics(boxes)`** — 화면이 스스로 내는 단위. `h`(글자 높이 중앙값)와 `x0·x1·span`(내용의
   가로 범위). 이미지 높이는 **쓸 수 없다** — 스티칭되면 종목 수에 따라 늘어나 배율이 아니다.
   `bind()`는 이제 이미지 크기를 **인자로 받지 않는다**(두 번째 진실의 출처 제거).
2. **최근접 분할로 허용치를 없앴다.** 데이터 박스는 헤더 박스보다 넓어 오른쪽 끝이 60~65px
   어긋나는데(밴드 간격 348~381px의 **0.18배**), 허용치가 `2.2 × 글자높이`에 묶여 있어 폭 2배에서
   **모든 금액이 탈락하고 헤더 화면이 0행**이 됐다. 이 어긋남은 글자 크기가 아니라 **레이아웃
   거리**다. 가장 가까운 밴드에 배정하면 상수가 아예 없어진다 — `rows_from_list`가 이미 쓰던 방식.
3. **행 경계를 개수가 아니라 간격으로.** 앵커 열 금액을 `depth`개씩 잘라 행을 만들고 있었다.
   그러면 한 행에서 금액이 하나만 어긋나도 **그 뒤 모든 행이 밀린다**(측정: 행 간격을 10%만
   좁혀도 재현율은 31/31인데 value 22/31 — 값이 이웃 행에서 온다). `_large_mode`로 간격 분포에서
   행 경계를 찾게 바꿨다. 복제 ×16에서 **8행 → 144행**으로 고쳐졌다.

`_large_mode`는 **무차원 조건 둘**로만 동작한다(거리 단위가 없어 어떤 배율에서도 같은 자리를 찾는다):
- **첫 도약**을 쓴다 — 가장 큰 도약이 아니다. 계좌 구분자가 있는 화면은 `행 안 | 행 사이 |
  블록 사이`로 **세 무리**이고, 큰 도약을 고르면 블록 경계를 집어 한 블록이 통째로 한 행이 된다.
- **질량 조건** — 큰 무리가 표본의 25%를 못 넘으면 무리가 아니라 이상치다(측정: 간격 33개 중
  3개(9%)에서 갈려 피치가 113 → 968로 뛰고 화면이 0행이 됐다).

### 시뮬레이터가 세 번 거짓말했다 — 도구를 먼저 의심하는 편이 빨랐다

기기 변환은 순진하게 짜면 전부 틀린다. 세 번 다 **bind가 아니라 도구**가 원인이었다:

| 증상 | 실제 원인 |
|---|---|
| 폭 2.0배에서 헤더 화면 0행 | x만 늘려 **우측 정렬이 깨짐**. '넓은 화면'이 아니라 '정렬이 무너진 화면'을 재고 있었다 |
| 행 간격 2.0배에서 행 수가 2배 | y를 통째로 늘려 **줄 안의 y 흔들림까지** 늘어남 → 한 줄이 두 줄로 쪼개짐 |
| 본문 복제 ×4에서 0행 | 같은 문구를 반복하면 `rows_from_list`가 **설계대로 'UI 크롬'으로 지운다** |

마지막 것이 특히 교훈적이다. 복제 프로브는 사본마다 이름에 접미사를 붙이고 금액에 서로 다른
배수를 걸어야 유효하다(배수를 세 값에 똑같이 걸면 회계 항등식은 보존된다). 항등식 검사에서
**현금·예수금 행은 빼야 한다** — 취득원가가 없어 `value = cost + pnl`이 원래 성립하지 않는다.

### 곁가지 — OCR에 리사이즈해서 넣으면 이득인가: **아니다**

비전 LLM 경로는 이미지를 **절반으로 줄여서** 넣는다(`resample_half_b64`). 같은 걸 OCR에도
하면 이득인지 쟀다(§4.10의 배율 불변 수정 덕에 이제 좌표가 줄어든 채로 와도 bind가 받는다).

| 입력 배율 | 8장 wall | 파리티 |
|---|---|---|
| 1.0 (원본) | 11.9s | **PASS** |
| 0.85 | 12.7s | PASS |
| 0.681 (짧은변 736) | 11.3s | PASS |
| 0.6 | 10.7s | **FAIL** |
| 0.5 | 11.1s | PASS |
| 0.4 | 10.8s | **FAIL** |

단일 화면(1080×4928)에서 단계별로, 양성 대조군(배율을 **키워도** 시간이 느는가)까지 포함:

| 배율 | 픽셀 | 검출 | 인식 | 박스 수 |
|---|---|---|---|---|
| 0.5× | 1.3Mpx | 0.62s | 1.09s | 65 |
| 1.0× | 5.3Mpx | 0.62s | 1.10s | 68 |
| 1.5× | 12.0Mpx | 0.66s | 1.05s | 67 |
| 2.0× | 21.3Mpx | 0.67s | 0.99s | 67 |

**픽셀을 16배 늘려도 총 시간이 안 변한다.** 비용을 정하는 것은 픽셀이 아니라 **글자 박스 개수**다
(인식이 검출의 두 배를 쓰고, 박스 수는 배율과 무관하게 65~68로 일정하다). 검출기도 입력을
내부에서 정규화하므로 더 주는 것도 덜 주는 것도 값을 바꾸지 않는다.

> **두 엔진은 비용 구조가 다르다.** 비전 LLM의 prefill은 **면적에 비례**하는 토큰을 만들어
> 절반 리샘플이 4배 이득이다. OCR은 **글자 수에 비례**한다. 한쪽에서 옳은 최적화가 다른 쪽으로
> 옮겨지지 않는다 — 그래서 재보기 전에는 옮기면 안 된다.

결론: **원본 그대로 넣는다.** 이득이 없고, 공격적으로 줄이면 파리티가 흔들린다(0.6·0.4 FAIL).
`IMG_SCALE`은 프로브용 노브로만 남기고 기본값은 1.0이다.
(단, 이건 Orin + RapidOCR 측정이다. 폰의 ML Kit은 다른 엔진이라 미측정이다.)

- 복제 프로브에서 **요약 화면만** 행 수가 부푼다(+53~70%). 복제된 카테고리 라벨이 그 자체로

- 이 수정들은 ML Kit 봉투(§4.8, R∈[0.6,1.8])와 기준 파리티(컨트롤 4종 포함)를 **그대로 통과**한다.

## 4.11 행 간격 축 완결 — 그리고 도구가 가리고 있던 진짜 결함

§4.10에서 이 축만 남겨뒀다. "시뮬레이터를 신뢰하지 않는다"고 적었는데, **의심의 방향이
반쯤 틀렸다**: 도구가 타던 결함이 도구만의 것이 아니라 **프로덕션에도 있었다.**

### ① 줄 묶기가 이어 붙고 있었다 — 기준 상태에서도

`group_lines`가 `abs(_cy(b) - _cy(cur[-1])) <= med_h*tol`로 **직전 박스와** 비교했다. 한 칸씩
조금씩 밀리면 서로 다른 줄이 한 줄로 이어진다(chaining drift). 변환을 걸지 않은 **원본 8장에서**:

| | 현재(체이닝) | 대표값 기준 |
|---|---|---|
| 한 '줄'의 최대 세로 폭 | **112px (글자높이 53의 2.1배)** — 2장에서 발생 | 전 화면 30px 이하 |

같은 결함을 `ocr.merge_lines`와 ML Kit 시뮬레이터에서 이미 한 번씩 고쳤었다. **세 번째로 같은
버그를 만난 것은 사본이 셋이었기 때문**이라, 줄 묶기를 `bind.group_lines` 하나로 합치고
`ocr._rows_of`는 그걸 부르게 했다(지연 임포트 — 어댑터 계층이 모듈 로드 시점에 바인더를 끌고
오지 않도록).

고친 뒤 **성긴 방향이 전부 열렸다**: 2.5배·3.0배가 FAIL → PASS.

### ② 마지막 글자높이 창 — 촘촘해지면 이웃 행을 빨아들인다

남은 실패는 촘촘한 쪽뿐이었고, 증상이 좁았다: 행 수·재현율·금액은 전부 정상인데 **수량만 2행에서
유실**(qty 29/31), 둘 다 가장 촘촘한 화면. 원인은 행에 딸린 조각(종목명·수량)을 걷는 세로 창
`1.3 × 글자높이`였다. 행이 촘촘해지면 이 창이 **옆 행에 닿는다.**

행 경계 간격(`thr`, §4.10에서 이미 데이터에서 구하고 있다)의 **절반**으로 바꿨다 — 정의상
이웃 행에 닿을 수 없고, 레이아웃 밀도를 따라 같이 움직인다. `bind.py`에서 마지막 글자높이
상수가 사라졌다.

### 봉투 — 배율이 아니라 **밀도**로 적는다

배율은 우리 픽스처에만 의미가 있다. 기기 무관한 값은 **밀도 = 줄 피치 / 글자 높이**다:

| 배율 | 최소 밀도 | 판정 |
|---|---|---|
| 0.6 | 0.90 | FAIL |
| 0.7 | 1.05 | FAIL |
| **0.75** | **1.13** | **PASS ✅** |
| 0.85 | 1.28 | PASS |
| 1.0 (원본) | 1.42 | PASS |
| 3.0 | 4.25 | PASS |

**밀도 1.13 이상이면 통과한다.** 실패 구간(≤1.05)은 줄 사이 여백이 글자 높이의 5%도 안 되는
화면이다. 우리가 본 가장 촘촘한 실제 화면이 1.42이므로 **약 25%의 여유**가 있다. 다만 이건
"이보다 촘촘한 UI는 없다"는 증명이 아니라 **여유의 크기**일 뿐이다.

### 회귀 없음

기준 파리티(컨트롤 4종) · ML Kit 봉투 R∈[0.6,1.8] · DPI 0.5~3.0 · 폭 0.8~3.0 · 긴 화면 ×32 ·
VLM 라벨 심판 — **전부 그대로 통과**한다.

> **교훈:** 도구를 의심한 것은 옳았지만 "도구만의 문제"로 넘긴 것은 틀렸다. 합성 변환에서만
> 보이던 드리프트가 원본에도 있었고, 변환은 그걸 **증폭해서 보여준 것**이었다. 시뮬레이터가
> 거짓 경보를 세 번 낸 뒤라 네 번째도 도구 탓으로 접을 뻔했다 — 접기 전에 **원본에서 같은
> 양을 재본 것**이 갈랐다.

### 먼저 — OCR 오독은 OCR 층에서 못 고친다 (측정으로 종결)

`IVV`→`IWV`를 끝까지 팠다. 크롭을 4배로 키워 보면 `I` 다음 네 사선이 `V+V`인지 `W`인지
**획으로 구분되지 않는다**(커닝이 좁아 두 V가 붙어 W의 잉크가 된다).

| 설정 | `IVV` 크롭 | `알파벳 A` 크롭 |
|---|---|---|
| korean PP-OCRv5 mobile (**프로덕션**) | `'IWV'` 0.899 | `'알파벳A'` 0.985 |
| korean PP-OCRv4 mobile | `'WV'` 0.771 | `'알파벳A'` 0.992 |
| ch PP-OCRv5 mobile | `'IW'` 0.646 | `'A'` 0.985 |
| PP-OCRv6 rec small | `'IW'` 0.906 | — |
| 프로덕션 + 2× / 4× / 8× 확대 | `'IWV'` 0.901 / 0.899 / **0.898** | — |

**프로덕션 모델이 넷 중 제일 낫고, 8배 확대까지 소수점 셋째 자리가 같다**(스케일 불변 실패 —
§3의 cls 사례와 같은 시그니처). 공백 유실도 네 모델 공통이다. 검색으로도 못 가른다:
자동완성은 `IVV`→IVV, `IWV`→IWV로 **둘 다 실재 ETF**라 오독이 조용히 성공한다.

**가르는 근거는 시세뿐이다.** 화면 단가 751.18 / `IVV` 캡처일 종가 **749.06(−0.28%)** /
`IWV` 424.96(+76.8%) / 다른 혼동 후보 `IVW` 136.25 · `IVA` 4.39 · `IWM` 293.48.

> **글리프에는 정보가 없고 시세에는 있다. 그래서 고칠 자리는 OCR이 아니라 채택 게이트다.**

### 설계 — 식별자는 **가설**, 채택 근거는 **시세** 하나

심볼 게이트는 이미 절반을 갖고 있었다(설명되지 않는 심볼을 버린다). 버린 뒤 **근거를 갖고
고치는 나머지 절반**을 붙였다:

1. `resolve.confusable_variants(token)` — 편집거리 1, **같은 혼동류 안에서만**
   (`{V,W,U,Y}` `{I,l,1,T}` `{O,0,D,Q}` `{S,5}` `{B,8}` …). `IWV`→`IVV`가 후보에 든다(13개).
   시세도 심볼도 모르는 **순수 문자열 함수**다.
2. `server._arbitrate_symbol` — 후보를 자동완성으로 실재 확인 → 캡처일 종가가 화면 단가를
   `SYMBOL_TOL`(기존 상수) 안에서 설명하는 것이 **정확히 하나**일 때만 채택하고
   `symbol_src="corrected:price-arbitration"`과 근거 문장을 남긴다.
   **0개거나 2개 이상이면 교정하지 않는다** — 기존대로 비우고 경고한다.
3. `resolve._script_pieces` — 질의 폴백에 한글↔라틴 경계 분해를 더했다. 자동완성은
   `알파벳A`도 `알파벳 A`도 못 풀고 `알파벳`만 GOOGL을 준다(측정). 원인은 공백 자체가 아니라
   **토큰 폴백이 공백에서만 쪼개는 것**이었다 — §3의 "공백 하나 차이" 서술을 이걸로 정정한다.

음성 대조 5종 전부 통과: 후보가 둘 이상 설명되면 교정 안 함 / 시세 없음 → 교정 안 함 /
설명되는 후보 0개 → 교정 안 함 / 국내 6자리 코드는 대상 아님 / 하나만 설명 → `IVV` 채택.

### 코퍼스가 드러낸 파이프라인 결함 6건 — **전부 값·라벨을 조용히 오염시키던 것들**

**① 증권사 검색의 무근거 폴백 — 지어내고, 게다가 비결정적이었다.**
`use_llm=False`(엣지 기본)에서 `search_broker`는 검색 결과 텍스트의 **최빈 `○○증권`**을
답으로 썼다. 라벨 6종으로 재보니 **6개 중 5개를 지어냈다**:

| 라벨 | 최빈이 낸 답 | 실제 |
|---|---|---|
| `Super365` | **대신증권**(2회) vs 메리츠증권(1회) | 메리츠증권 |
| `보유계좌`(화면 제목) | 지분증권 | 브랜드 아님 |
| `종합잔고`(화면 제목) | 나무증권 | 브랜드 아님 |
| `한화오션`(종목명) | — | 브랜드 아님 |
| `TIGER 미국나스닥100`(종목명) | 신한투자증권 | 브랜드 아님 |
| `my자산현황`(화면 제목) | 유가증권 | 브랜드 아님 |

근접도(브랜드 토큰과의 거리)로 바꿔봐도 같이 지어낸다(`보유계좌`→다올투자증권,
`TIGER…`→키움증권). **검색 텍스트 마이닝 자체에 분별력이 없다** → 임계값으로 덮지 않고
**단계를 없앴다**(각도 분류기 cls를 껐을 때와 같은 판단). 그리고 검색 순위가 호출마다 달라
**같은 스크린샷이 다른 증권사를 냈다** — 한 세션 안에서 메리츠/대신이 갈렸다.

세 가지를 함께 고쳤다:
- `search_broker`: `use_llm=False`면 **None**(폴백 없음). 캐시에 확정된 답이 있을 때만 풀린다.
- **캐시를 실제로 넘긴다.** `server.extract_batch`는 `finalize`에 `broker_cache`를 **주지
  않고** 있었다 — 요청마다 재검색했다는 뜻이다. 채점기(`parity.py`)도 같이 넘기게 했다.
- 라이브 캐시 6개 중 **오염 5개를 폐기**했다(백업 후). 남은 것은 `super365→메리츠증권` 하나.
- `finalize`: 증권사 라벨이 그 화면의 **종목명과 같으면** 열이 잘못 채워진 것이므로 검색하지
  않는다(`한화오션`·`TIGER…`가 캐시에 들어간 경로를 막는다).
- `broker_src`(`screen`/`inherited`/`research`)를 남긴다 — 다른 필드의 `*_src` 규약과 동일.

**② `잔고구분`이 금액 열로 오분류돼 행이 통째로 밀렸다.**
mPOP의 가로 스크롤 표에서 열 구성이 `평가금액·매수금액 | 보유수량·잔고구분`일 때,
`잔고구분`이 `H_VALUE`의 `잔고`에 걸려 value 열이 됐다. 그 밴드는 한 행에 숫자가 하나뿐이라
**다음 행의 수량이 이 행의 평가금액으로** 들어갔다(실측: `qty=3,146,613 / value=30`, 이름은
두 종목이 이어 붙음). `H_CATEGORY = ("구분","유형","상태")`를 `_kind_of` 맨 앞에 두어
분류 열이 밴드를 만들지 않게 했다. E그룹 img5/6/7이 5/4/2행 → **9/7/4행**으로 복구.

**③ 예수금 상세 화면이 같은 돈을 2~3행으로 냈다.**
화면은 잔고 하나를 시점별(`당일`·`D+1`·`D+2`)과 내역(`현금`·`수표`·`청약증거금`)으로 보여준다.
미결제가 없으면 값이 같아 기존 중복 제거가 접었지만, 미결제가 있으면 값이 달라 각각 살아남았다
(실측 07-21: 48,789,151 + 44,186,151 + 40,225,651). **어느 시점이 자산인지는 추측하지 않는다** —
같은 앱 요약 화면의 `원화예수금` 총액과 일치하는 시점이 답이다(실측 07-29: 요약 36,682,999 =
**D+2**, 앱 헤드라인도 `원화 예수금 (D+2)`). 대조할 총액이 없으면 **접지 않고** 게이트가 울게 둔다.

**④ UI 어포던스·자기 값을 단 라벨이 보유행으로 들어왔다** (`접기›`, `환율 1,482.00`).
앱별 어휘를 늘리지 않고 형태로 갈랐다: 이름이 `›»⌄>`로 끝나면 누를 수 있는 것이고,
이름 안에 `1,482.00`처럼 자리수구분 쉼표·소수점이 있으면 그 라벨이 자기 값을 달고 있는 것이다.

**⑤ 쉼표를 마침표로 읽어 손익이 1000분의 1이 됐다.**
화면 `+3,662,786원`을 OCR이 `+3,662.786원`(conf 0.98)으로 읽었다. `cost`는 `value − pnl`로
**파생**되므로 회계 항등식이 그대로 성립해 게이트가 침묵했다(실측: `IVV` cost가 22,042 대신
24,538). `IVV`→`IWV`와 같은 글리프 혼동인데 이쪽은 **금액의 크기**를 바꾼다.
자리수 구분은 세 자리씩이고 이 화면들의 금액은 원화 정수·달러 두 자리다 → `,\d{3}\.\d{3}$`는
쉼표 오독으로 되돌린다. 달러 2자리(`1,234.56`)·환율(`1,509.90`)·수익률은 건드리지 않는다(검증).

**⑥ 출처 없는 `price`를 그대로 내보내고 있었다.**
비전 모델이 낸 `price`가 표시 항등식(`qty×price≈value`)을 통과하면 **출처 없이** 살아남았다.
이 화면들엔 단가 열이 아예 없으므로 그 숫자는 모델이 계산했거나 지어낸 것이다. 우리가 확인한
두 값으로 다시 계산해 `computed:value/qty`를 붙인다(항등식을 통과했으므로 값은 2% 안에서 같다 —
바뀌는 것은 **출처의 유무**뿐). VLM 경로 `price_src` **20/31 → 31/31**.

### 라벨의 독립 심판을 종목명까지 확장

§4.9의 broker 심판을 `name`에도 걸었다(`finalize._name_supported`). 이름은 행의 식별자라
**비우지 않고** `name_src="unverified"` + 경고만 낸다. 근거가 되는 OCR 자신도 글리프를 틀리므로
완전 일치를 요구하지 않고 **이름 길이만 한 창**을 밀며 유사도 0.6 이상을 근거로 인정한다.

### 하네스 자신의 결함 2건 (측정을 왜곡하고 있었다)

## 4.13 외부 네트워크 — 나가는 것 전부 (단일 통로 `agent/outbound.py`)

프라이버시 주장은 나가는 것을 **열거할 수 있을 때만** 검증 가능하다. 아웃바운드를 함수 하나로
모으고 목적마다 무엇이 나가는지 적었다. 여기를 지나지 않는 외부 요청은 없다.

| 목적 | 호스트 | 나가는 것 | 언제 | 없으면 |
|---|---|---|---|---|
| `symbol` | `ac.stock.naver.com` | **종목명 한 개** (`엔비디아`) | 추출 중, 행마다 1회(캐시) | `symbol=None` → 시세·수량 유도 불가, 화면값만 |
| `quote` | `query1.finance.yahoo.com` | **심볼 한 개**(환율 폴백은 `KRW=X`) | 추출 중 + 예약 갱신 | 통화 판정·T3·T4 수량 유도·재평가가 꺼진다 |

> **환율은 1순위가 네트워크가 아니다.** `enrich.get_fx()`는 화면의 외화예수금 행에서
> `원화 평가금액 ÷ 달러 잔액`을 먼저 읽는다(비율이 500~3000이면 채택). Yahoo `KRW=X`는
> **그 행이 없을 때만** 부르는 폴백이다 — 픽스처 8장 실행에서는 온라인·오프라인 둘 다
> 화면값 1,509.90을 쓰고 환율 조회가 나가지 않는다.
| `broker` | `search.naver.com` | **브랜드 토큰 한 개** (`Super365`) | 캐시에 없는 브랜드에서만 | `broker=None` + `증권사 미상` 경고 |

**절대 나가지 않는 것: 스크린샷 · 금액 · 수량 · 계좌번호 · 계좌별칭.**
`127.0.0.1`(ollama·WebView)은 기기를 벗어나지 않으므로 이 표의 대상이 아니다.

스위치 `PF_OUTBOUND`: `all`(기본) / `prices`(증권사 검색만 차단) / `none`(전부 차단).
`none`에서 **추출은 그대로 되고 시세·심볼만 빈다** — 프라이버시 게이트를 이걸로 실증한다.
APK는 `prices`로 고정한다(§아래).

### 짚어야 할 모순 3건

**① "검색어는 민감정보가 아니다"는 `broker`에만 맞다.**
`symbol`·`quote`로 나가는 것은 **보유 종목명과 심볼**이다. 금액·수량은 안 나가지만
*무엇을 갖고 있는지*는 나간다. 그리고 이 레포는 스스로 그것을 민감정보로 취급한다 —
`.gitignore`가 `watchlist.json`·`prices.json`을 **"보유 종목 구성 노출이라 공개 레포 금지"**로
막고 있다. 같은 정보가 커밋은 금지인데 외부 API로는 나가는 상태다.
더 센 것은 **예약 갱신**(`server.refresh_prices`)이다 — 추출과 무관하게 정해진 시각에
`watchlist.json`의 **심볼 목록 전체**를 한 번에 조회한다. 한 종목씩 흩어지는 것보다
포트폴리오 구성이 더 잘 드러난다.
→ 판단은 사용자 몫이지만 **정확히 이렇게 적어둔다.** 줄이려면 `PF_OUTBOUND=none`으로
추출만 돌리고 시세를 포기하거나, 시세 조회를 배치·지연·더미 혼입으로 흐리는 방법이 있다(미구현).

**② APK가 얻지도 못할 검색을 내보내고 있었다.**
`server.extract_batch`가 `finalize(use_llm=True)`(기본값)로 부르는데 폰에는 ollama가 없다.
그래서 브랜드 웹검색은 **나가고**, 검증할 LLM이 없어 실패해 `None`이 됐다 — 값도 못 얻고
요청만 나간다. `android_main.py`가 `PF_OUTBOUND=prices`를 고정해 아예 나가지 않게 했다.

**③ 문서가 `broker` 검색을 빼먹고 있었다.**
`android/README.md`와 A3 체크리스트가 "나가는 통신은 심볼·시세·환율 조회뿐"이라고 적어
증권사 브랜드 검색을 누락했다. 이 표로 정정한다.

### 실증 — `PF_OUTBOUND=none`으로 픽스처 8장 (실측)

| | 결과 |
|---|---|
| 재현율 · 환각 | **31/31 · 0** ✅ |
| `value` · `cost` · `broker` · `accountType` | **31/31** ✅ — 화면에서 읽는 것은 전부 온전 |
| `qty` | 24/31 — 화면에 수량이 없어 T3·T4로 **유도하던** 7행이 빈칸 |
| `price` | 14/31 — USD 자산이 원화 표기로 남음. **환율 때문이 아니다**(1,509.90 정상 획득) |
| `name` | 29/31 — `IWV`→`IVV` 시세 중재가 못 돈다 |
| 게이트 | 침묵 |

빠지는 기전을 정확히 적는다 — **환율도 심볼도 아니고 시세다**:

```
symbol=AIPO      ← .symbol-cache.json 에서 (네트워크 불필요)
fx=1509.9        ← 화면 외화예수금 행에서 (네트워크 불필요)
close=None       ← 차단
  → 심볼 게이트가 판정을 건너뜀 → `_value_krw` 미설정
  → 화면 금액이 원화인지 달러인지 모름 → FX 환산 불가 → price가 원화로 남음
```

즉 시세 하나가 막히면 **통화 판정 → 환산 → 수량 유도 → 식별자 중재**가 연쇄로 꺼진다.
**빠진 칸은 전부 외부 근거가 필요한 칸이고, 어느 것도 지어내지 않았다.**
파리티 판정은 FAIL이지만 그건 정답표가 온라인 값 기준이기 때문이고, 이 실행의 목적은
'추출이 네트워크 없이 성립하는가'다 — 성립한다.

캐시가 답을 대신 내주고 있으면 "동작한다"는 말이 무의미하다. 심볼 캐시(65개)·증권사 캐시·

## 5. 파이프라인 결함 발견 — 심볼 검증이 수량 게이트보다 **뒤에** 있었다

`server.enrich`는 화면 수량 게이트를 먼저 돌리고 심볼 검증 게이트를 나중에 돌렸다. 그래서
**아직 검증되지 않은 심볼의 참가격으로 화면 수량을 기각**한다.

측정: `IVV`가 `IWV`로 오독되면 → `IWV`는 실재 ETF라 해석 성공 → 그 시세로 화면에 멀쩡히 적힌
`33주`가 기각됨 → T4가 엉뚱한 시세로 `58주`를 유도. 순서를 뒤집어 심볼을 **먼저** 기각하면
`symbol`이 사라져 수량 게이트가 그 행을 건너뛰고 화면값을 지킨다 → `qty`·`qty_src` 31/31.

**이 결함은 OCR이 드러냈을 뿐, 비전 LLM이 티커를 오독해도 똑같이 발생한다.**
`agent/server.py`(공유 파이프라인) 변경이므로 **머지 전 승인 필요.**

교훈: 게이트는 순서가 의미다 — 신뢰하지 않기로 한 근거로 다른 값을 기각하면 안 된다.

### A2 검증 범위 — 서버 자동, 브라우저는 육안

서버 경로는 실제 `/extract/batch`로 확인했다(31 holdings·게이트 0·45.6s). 그러나 앱→표 렌더까지
가는 `eval/harness/e2e.py`(Selenium)는 **돌리지 못했다** — snap Firefox + geckodriver가 aarch64
헤드리스에서 기동 단계에 멈춘다(150s·900s 모두 무출력 타임아웃). HANDOFF.md가 이미 기록한
aarch64 드라이버 문제로, 엣지 경로와 무관한 기존 툴링 이슈다.

대신 **사용자가 브라우저에서 직접 확인**했다(2026-07-31): `http://<host>:8898/` 에서 URL 입력 없이
같은 오리진이 자동 채택되고 표·출처 칩까지 정상 렌더. 자동화 회귀 테스트는 없고 **육안 1회**다 —
`e2e.py`는 aarch64 snap firefox 문제가 풀려야 붙는다.

### 스파이크 기동 (이 명령을 쓴다 — 손으로 조립하지 말 것)

```bash
PORT=8898 DATA_DIR=$HOME/portf-agent/data-spike \
EXTRACT=ocr OCR_ENGINE=rapidocr SAVE_CAPTURES=1 \
  /home/omr/workspaces/edge-ocr-venv/bin/python agent/server.py
```

`CAPTURES_DIR`은 **일부러 지정하지 않는다.** 기본값이 `DATA_DIR/../captures`라
`DATA_DIR`을 바꿔도 `~/portf-agent/captures`로 수렴한다 — 라이브와 스파이크 업로드가
한 폴더에 모인다. **이건 의도된 동작이다**(사용자 결정, 2026-07-31): 백업의 목적이
실제 업로드를 진단용으로 모으는 것이라 스트림을 쪼갤 이유가 없다. 어느 경로로 들어온
캡처인지는 `result.json`의 내용(OCR vs VLM 원문)으로 구분된다.

**사고 기록(2026-07-31):** 스파이크 서버를 손으로 띄우면서 `SAVE_CAPTURES`를 빠뜨려
**하루치 업로드가 백업 없이 사라졌다**(복구 불가 — `save_capture_batch`가 유일한 저장 지점).
원인은 단순 누락이 아니라 **기동 경로가 이 플래그를 소유하지 않았던 것**이다:
`run-agent.sh`가 `MODEL`·`DATA_DIR`·`PORT`·`NP`·`EXTRACT`만 export하고
`SAVE_CAPTURES`는 넘기지 않아, 외부에서 안 주면 조용히 꺼졌다.
→ `run-agent.sh`에 `SAVE_CAPTURES` 기본값 1을 넣어 기동 경로가 소유하게 했다.
관측 도구는 **기본이 켬**이고 끄는 쪽이 명시적이어야 한다.

주의(선반영 상태, 이 작업과 무관): 시스템 `numpy`가 이미 깨져 있다 —
`/usr/lib/python3.10/dist-packages/numpy`가 `__init__.py` 없는 2023년 잔해이고 dpkg는
`python3-numpy 1.21.5`가 설치됐다고 보는데 파일이 없다. 그래서 OCR은 전용 venv를 쓴다.
